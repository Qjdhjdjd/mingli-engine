# 大模型解读：接入方式、约束与实测

这份文档说明「大模型解读」这一层是怎么接的、它能做什么、不能做什么，以及怎么验证它没有胡说。

## 一、为什么不是「让大模型算命」

最容易做的版本是：把生日丢给模型，让它自由发挥。这个版本我不做，原因不是技术，是它会毁掉前面所有工作：

- 规则引擎的每条结论都能回指到「哪本书的第几条」。模型自由发挥的结论，回指不到任何地方。
- 一旦模型开始自己判吉凶，同一张盘问两次会得到两个答案，而且都"很有道理"。
- 你无法区分「模型读懂了规则」和「模型编了一段像命理的话」——这两件事在文本上几乎无法分辨。

所以这一层的定位是**解释器**，不是**判断器**：

> 规则引擎负责「算出什么」，大模型负责「讲清楚」。

吉凶、分值、命中的条款，一个都不由模型产生。

## 二、三段式结构

```
排盘结果 ──► 事实清单(JSON) ──► 大模型 ──► 校验器 ──► 展示
              │                              │
              └── 只含已命中的规则与编号      └── 查引用、查分值、查绝对化措辞
```

### 第一段：事实清单（`src/llm/facts.py`）

把报告压成一份结构化 JSON，只保留：

- `computed`：四柱、日主、强弱、格局、五行占比、刑冲合害、神煞、调候
- `judgments`：命中的规则，每条含 `id / book / title / verdict / score / text`
- `overall`：等级、均分、命中条数

条目上限 26 条，超出按分值绝对值取前 26 并标注 `truncated`，避免上下文被长盘撑爆。模型看不到规则库全表，也看不到任何未命中的条款。

### 第二段：生成（`src/llm/prompts.py` + `provider.py`）

提示词写死了七条铁律：只能用清单内条目、每句判断必须带 `[编号]`、不得改分值、不得绝对化、不得预测具体事件、不得虚构书名、平实说明文。

但提示词本身不构成保证——模型可以不听。所以真正的约束在第三段。

### 第三段：校验（`src/llm/verify.py`）

程序对生成文本做四项检查：

| 检查 | 方法 | 触发后动作 |
|---|---|---|
| 引用了不存在的编号 | 正则抽出所有 `XX-000`，与清单比对 | 致命，自动降级为本地模板 |
| 编造了分值 | 抽取「+3 分」「−2分」形式，与真实分值比对 | 致命，自动降级 |
| 绝对化措辞 | 「必然」「注定」「百分之百」「N% 的概率」 | 记录并展示，不降级 |
| 无出处的判断 | 句中有「吉/凶/宜/忌/利/妨/损/益/祸/福」但整段无编号 | 超过 20% 则判不通过 |

引用采用「编号置于句末，视为对该段前文的引用」这一学术惯例：段内一句话末尾带 `[LR-22]`，它前面几个分句都算有出处。

校验结果会直接显示在界面上：`校验通过 · 引用规则 9/12 条`，或红色的 `校验未通过：…` 加具体问题列表。**这一步不能省**——它是你能判断"这段文字值不值得看"的唯一依据。

## 三、两种模式

| 模式 | 允许模型做什么 | 适合 |
|---|---|---|
| `strict`（默认） | 只能解释已命中的条目 | 想看清「按古法这张盘怎么判」 |
| `exploratory` | 四段之后可另起「【模型推断】」段做类比联想 | 想看模型自己的联想，但要求它标注清楚 |

`exploratory` 模式下，「【模型推断】」之后的内容会被单独切出来，界面上用米色底、左侧竖线区分，并标注「非典籍结论，已被隔离」。这一段不参与校验统计，但如果模型在这一段里伪造规则编号，同样判失败。

## 四、配模型

支持任何 OpenAI 兼容的 `/chat/completions` 接口。内置预设：

| provider | base_url | 默认模型 |
|---|---|---|
| `deepseek` | https://api.deepseek.com/v1 | deepseek-chat |
| `moonshot` | https://api.moonshot.cn/v1 | moonshot-v1-8k |
| `qwen` | https://dashscope.aliyuncs.com/compatible-mode/v1 | qwen-plus |
| `openai` | https://api.openai.com/v1 | gpt-4o-mini |
| `ollama` | http://127.0.0.1:11434/v1 | qwen2.5:7b（本地，无需 Key） |

两种配置方式，环境变量优先于文件：

```bash
# 方式一：环境变量
export MINGLI_LLM_PROVIDER=deepseek
export MINGLI_LLM_API_KEY=sk-xxxx
export MINGLI_LLM_MODEL=deepseek-chat
python app.py
```

```jsonc
// 方式二：config/llm.json（把 config/llm.example.json 复制过去改）
{
  "provider": "deepseek",
  "base_url": "https://api.deepseek.com/v1",
  "api_key": "sk-xxxx",
  "model": "deepseek-chat"
}
```

**不要配也可以。** 未配置时按钮照常工作，走本地模板：同样分四段、同样逐条带编号、同样过校验。模板是基准线，不是残次品——它证明「带出处地讲清结论」不需要大模型也能做到。

想验证在线链路但手头没有 Key，可以起自带的假模型：

```bash
python tools/mock_llm.py 8799
# 另一个终端
MINGLI_LLM_PROVIDER=custom MINGLI_LLM_BASE_URL=http://127.0.0.1:8799/v1 \
MINGLI_LLM_API_KEY=sk-mock MINGLI_LLM_MODEL=mock-reasoner python app.py
```

## 五、实测结果

| 场景 | 结果 |
|---|---|
| 七种模板（八字/六爻/梅花/择日/姓名/流日区间/流日单日） | 全部校验通过，无未溯源句 |
| 模型返回合规文本 | 原样采用，标注 provider 与耗时 |
| 模型返回伪造编号 | 触发一次定向重写；仍失败则降级模板，界面显示原因 |
| 模型服务不可达 / 401 / 超时 | 捕获后降级模板，不抛异常给用户 |
| 请求体含 API Key | 有测试断言：发给模型的内容里不含 Key |

测试文件 `tests/test_llm.py`，23 个用例；全项目共 57 个测试。

## 六、它查不出什么（重要）

校验器能查「有没有出处」，查不出「出处对不对」。它有三处明确的盲区：

1. **用真编号说假话。** 模型可以引用一条真实命中的规则，却把它的意思讲反。程序能确认编号存在，不能确认语义一致。这一层需要人读原文核对——所以每条命中条目的原文都完整列在下方。
2. **不含吉凶词的事件预测。** 「明年适合换城市」「注意肠胃」这类话里没有「吉凶宜忌」，关键词规则抓不到。目前只能靠提示词约束，属于软约束。
3. **流利但空洞。** 四段俱全、句句带编号，却没有超出规则原文的信息量。这不算错误，但也没增加价值——模板本来就做得到。

换句话说：**校验通过 = 没有超出给定规则，不等于结论成立。** 这两句话在界面上都会显示，别只看前一句。

## 七、隐私与成本

**隐私**：一旦配置了在线模型，你的出生日期、时间、性别、四柱、命中的规则条目会以 JSON 形式发送给该模型服务商。这些是个人信息。用本地 `ollama` 可以完全避免外发；用云端 API 请自行判断是否接受。

**成本**：单次解读的输入约 2–4k token（取决于命中条数），输出约 500–800 token。按 DeepSeek 价位，一次约合人民币几厘到一分。没有缓存——同一张盘重复点击会重复计费。

**延迟**：实测取决于服务商，通常 3–15 秒。界面按钮在请求期间禁用，失败会显示具体原因而不是静默。

## 八、为什么这一层值得存在

规则引擎的输出是表格和条目，准确但不好读。模型的输出好读但不可信。这一层的价值在于**把两者接起来，并让「不可信」变成可测量的**：每一句有没有出处、引用的编号存不存在、有没有偷偷下新判断，全都摊在界面上。

如果哪天你发现某条解读"说得挺准"，正确的反应不是相信它，而是回到下面那一条规则，去看《渊海子平》原文到底怎么写的。这个动作才是这套工具想促成的。
